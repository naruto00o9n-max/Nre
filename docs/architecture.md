# قرارات المحرك

اختير تنفيذ Android أصلي صغير حول Android BitmapRegionDecoder وCanvas وDeflater، بدل ترحيل نموذج Skia قديم أو الاعتماد على SDK تجاري قبل إثبات قدرته على الصفحات الطويلة. لا يحتوي المشروع على كود من المشاريع المذكورة؛ الاستفادة منها كانت لدراسة نهج المقاطع وتحديد حدود المحررات البسيطة. لا نفترض معرفة بنية ibis Paint الداخلية.

## مسار البيانات

DocumentPicker → نسخة أصل دائمة → فحص الأبعاد فقط → BitmapRegionDecoder → مقاطع عرض مأخوذة العينات.

الإيماءات → تحويل إحداثيات الشاشة إلى إحداثيات الصورة → طبقات JSON → Renderer.

التصدير → فك شريحة بالدقة الكاملة → Renderer مع إزاحة موضع الشريحة → صفوف ARGB إلى RGBA → StreamingPng → ملف دائم → ورقة المشاركة.

الطبقات المتقاطعة مع حدود الشرائح تُرسم بالإحداثيات نفسها ويقصها Canvas عند الحدود. يجب إثبات غياب الفواصل باختبارات Android؛ صحة encoder وحدها ليست إثباتًا لصحة Canvas/decoder.

## خطة تحقق Android قبل وصفه بالاحترافي

1. ملف PNG بطول 50000 ثم 100000: استيراد، تصدير بلا تعديلات، مقارنة الأبعاد وكل البكسلات للمناطق المعتمة sRGB.
2. شفافية جزئية وICC وEXIF: قياس التحويلات وإما دعمها أو رفض المدخل بوضوح.
3. فرشاة ونص عربي يعبران عدة شرائح: مقارنة نتيجة التصدير بمرجع Canvas للصورة القصيرة، ثم فحص حدود الشرائح الطويلة.
4. تكبير وتنقل لمس متعدد، تبديل المصادر بسرعة، ضغط ذاكرة، إعادة فتح المشروع، خطوط مستوردة.
5. قياس ذروة الذاكرة وزمن التصدير على جهاز متوسط، لا استخدام محاكي فقط للحكم على الأداء.
6. ملف تالف، مساحة قرص غير كافية، رفض المشاركة، خروج التطبيق أثناء التصدير.

## الحدود الحالية

الرسم يعيد المرور على العمليات لكل إطار وشريحة؛ نحتاج فهرسة مكانية ودمج ضربات الفرشاة في طبقات حقيقية عندما تتزايد العمليات. cache المقاطع يعمل في خلفية واحدة لكن نقل الصورة عبر المصدر القديم يحتاج اختبار ضغط. الممحاة المستقبلية يجب أن تمسح طبقة الرسم فقط وألا تمس الأصل، وتحتاج تركيبًا معزولًا لكل طبقة.
